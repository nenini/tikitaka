# 쿨다운 후보 조회 튜닝 결과

## 적용한 변경

기존 쿼리는 `userAId`와 `userBId` 양방향 조건을 `OR`로 묶고
`CASE`와 `DISTINCT`로 상대 사용자 ID를 만들었다. 이를 방향별 조회 두 개와
`UNION ALL`로 분리했다.

- 각 방향이 기존 `IDX_match_pairs_user_a_cooldown`,
  `IDX_match_pairs_user_b_cooldown` 인덱스를 사용한다.
- Repository 반환 타입이 `Set<Long>`이므로 같은 상대와 여러 이력이 있어도
  Java에서 기존과 동일하게 중복 제거된다.
- 입력 후보 목록을 두 방향 모두 유지해 메서드의 기존 조회 범위를 보존한다.
- 기존 인덱스로 충분하므로 신규 인덱스와 Flyway 마이그레이션은 추가하지
  않았다.

## 실행 계획 비교

동일한 102,001건의 `match_pairs`와 9,999명의 후보를 사용했다.

| 구분 | 읽기 방식 | SQL 실행 시간 |
| --- | --- | ---: |
| 변경 전 | 102,001행 전체 스캔 + DISTINCT 임시 테이블 | 27.2 ms |
| 변경 후 | 방향별 쿨다운 인덱스 조회 + UNION ALL | 2.53 ms |

`EXPLAIN ANALYZE`의 단일 warm-cache 측정 기준으로 DB 내부 실행 시간이 약
90.7% 감소했다.

## 100회 반복 측정

5회 예열 후 기존 쿼리와 개선 쿼리를 같은 연결에서 번갈아 100회 실행했다.
아래 값에는 SQL 실행뿐 아니라 2,000행을 클라이언트로 받아오는 비용도
포함된다.

| 구분 | 결과 수 | 최소 | p50 | p95 | 최대 | 평균 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 변경 전 | 2,000 | 82.448 ms | 90.194 ms | 94.847 ms | 114.518 ms | 89.937 ms |
| 변경 후 | 2,000 | 59.922 ms | 65.971 ms | 69.665 ms | 84.142 ms | 65.665 ms |

- p50: 26.9% 감소
- p95: 26.5% 감소

대량의 바인딩 값 전송과 결과 역직렬화 비용은 두 쿼리에 공통으로 남기
때문에, 애플리케이션 관점의 개선율은 DB 내부 실행 시간 개선율보다 작다.

## 결과 동등성 및 회귀 검증

`cooldown-experiment.sql`에서 기존 결과와 개선 결과의 양방향 세트 차이가
모두 0건임을 확인했다. Repository 통합 테스트에는 다음 조건을 추가했다.

- 원본 사용자가 `userAId`인 이력
- 원본 사용자가 `userBId`인 이력
- 동일 상대와 복수 쿨다운 이력
- 쿨다운 기간이 지난 상대
- 입력 후보 목록에 없는 상대
- 빈 후보 목록

## 결론

이 병목은 인덱스 부재가 아니라 양방향 `OR`와 `DISTINCT` 때문에 기존
방향별 인덱스를 활용하지 못한 것이 원인이었다. 쿼리 구조만 변경해 결과
동등성을 유지하면서 전체 스캔과 임시 테이블을 제거했다.
