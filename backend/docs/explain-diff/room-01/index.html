Backend · ROOM-01 · LiveKit

대기방 상세 조회와
입장 권한 검증

확정된 매칭을 실제 소개팅 대기방으로 연결하고, 참여자만 일정·상대 요약·입장 가능 상태를 조회하도록 구성했다. LiveKit 접속 토큰은 아직 발급하지 않으며, 서버 측 Room 생성까지만 준비한다.

전후 차이

BEFORE · 매칭 확정까지만 존재

  • match_pairs에 확정 상태와 예정 시각만 기록
  • 대기방을 식별할 영속 데이터가 없음
  • LiveKit Room 이름과 참가자 연결이 없음
  • 사용자가 입장 가능한지 조회할 API가 없음

AFTER · 대기방과 LiveKit Room 연결

  • 매칭 확정 트랜잭션에서 대기방과 참가자 2명 생성
  • date-room-{matchPairId}로 LiveKit Room 이름 고정
  • 커밋 후 LiveKit 서버에 최대 2인 Room 생성
  • 참여자에게만 상세·입장 가능 상태 응답

매칭 확정부터 조회까지

01양쪽 수락MatchPair가 CONFIRMED로 전환되고 scheduledAt이 결정된다.
02DB 대기방 생성sessions와 session_participants에 방과 두 참여자를 저장한다.
03트랜잭션 커밋DB 저장이 성공한 경우에만 LiveKit 생성 이벤트가 실행된다.
04LiveKit Room 생성공식 서버 SDK로 최대 참가자 2명의 물리 Room을 준비한다.
05상세 조회JWT 사용자와 참여자 목록을 비교하고 입장 가능 시간을 계산한다.

입장 가능 시간 판정

18:50enterableFrom
19:00scheduledAt
19:10enterableUntil
TOO_EARLY · canEnter=falseAVAILABLE · canEnter=trueTOO_LATE · canEnter=false

상세 조회는 시간 전에도 허용한다. 그래야 프론트가 예정 시각과 카운트다운을 표시할 수 있다. 실제 LiveKit 토큰 발급 API에서는 canEnter=false일 때 409로 차단해야 한다.

누가 무엇을 관리하는가

MySQL

Room ID, 매칭 연결, 예정 시각, 참가자, 상태, LiveKit Room 이름을 영구 보존한다.

Backend

JWT 인증, 참여자 인가, 입장 시간 계산, LiveKit 서버 Room 생성과 API 응답을 담당한다.

LiveKit

실제 음성·영상 트랙과 실시간 참가자 연결을 관리한다. API 키와 Secret은 백엔드에만 둔다.

DB 마이그레이션 V15

sessions 확장

livekitRoomName을 추가하고 matchPairId와 Room 이름에 UNIQUE 제약을 적용해 하나의 확정 매칭이 중복 방을 만들지 못하게 한다.

기존 데이터 보정

이미 CONFIRMED인 match_pairs를 찾아 sessions와 session_participants에 대기방 및 두 참가자를 안전하게 백필한다.
