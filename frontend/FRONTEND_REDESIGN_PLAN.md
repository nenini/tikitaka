## 1. 문서 목적

`docs/design-system/`에 정리된 Tika 디자인 시스템을 바탕으로 현재 `/frontend`의 화면을 전면 개편한다.
이번 개편은 색상만 바꾸는 스킨 교체가 아니라 브랜드 인상, 정보 위계, 공통 컴포넌트, 화면 전환,
반응형 규칙을 하나의 제품 경험으로 다시 맞추는 작업이다.

이 문서는 다음 질문에 답하는 마스터 기획서다.

- 어떤 디자인 원칙을 전체 서비스에 적용할 것인가?
- 현재 시스템에서 무엇을 유지하고 무엇을 교체할 것인가?
- 43개 라우트를 어떤 화면군과 우선순위로 개편할 것인가?
- 디자인 시스템에 부족한 제품 UI 규칙을 어떻게 보강할 것인가?
- 어느 상태가 되면 화면 개편이 완료됐다고 판단할 것인가?

## 2. 배경과 현재 진단

### 2.1 현재 구조

- React 19 + TypeScript + Vite + Tailwind CSS 기반이다.
- 제품 화면은 43개 라우트, 페이지 성격의 TSX 파일은 약 36개다.
- 기존 `BloomTalk` 디자인 시스템은 `--bt-*`, `.bt-*` 계열로 구현돼 있다.
- 공통 UI 컴포넌트는 Button, Card, Field, Modal, Badge 등 23개가 이미 존재한다.
- TSX에서 `.bt-*` 참조가 약 1,000회 있어 일괄 삭제 방식은 회귀 위험이 크다.
- 화상 세션, 알림, 매칭, 리포트 등 비동기/실시간 상태가 많아 정상 화면 한 장만 디자인해서는 부족하다.

### 2.2 브랜드 정책

현재 저장소에는 세 이름이 공존해 왔다.

| 위치 | 사용 이름 |
|---|---|
| 새 디자인 시스템 | `Tika` |
| 현재 AppShell | `티키타카` |
| 기존 디자인 시스템 | `BloomTalk` |

본 개편의 최종 사용자 노출 서비스명은 **티키타카**로 확정한다. 현재 `/frontend/public`의
`tika-logo-black.png`, `tika-logo-whitever.webp` 로고 자산은 형태를 변경하지 않고 그대로 사용한다.
`BloomTalk`은 레거시 디자인 시스템 내부 명칭으로만 취급하고 사용자 노출 영역에서 제거한다.

### 2.3 확정된 개편 범위

- `/reports`, `/growth`를 전면 디자인 개편 범위에 포함한다.
- `/admin/*`은 별도 결정 전까지 사용자 화면 개편 이후의 보류 범위로 둔다.
- `public/main_hero_video.mp4`를 메인 페이지 히어로 영상으로 사용한다.
- 영상 기본 정보는 15초, 720×540(4:3), 24fps, 약 0.9MB다.

### 2.4 새 디자인 시스템의 강점과 보강점

새 시스템이 잘 정의한 영역:

- 시네마틱 인물 중심 비주얼과 아이보리·잉크·포레스트 색 조합
- 한 화면 한 메시지, 단일 Primary CTA, 넉넉한 여백
- 캡슐 내비게이션과 편집물 같은 이미지/텍스트 배치
- 이미지·영상 비율, 모션, 접근성, 반응형 기준

제품 UI를 위해 추가로 정의해야 하는 영역:

- 성공, 경고, 오류, 위험, 연결 상태 토큰
- 입력 검증, 로딩, 빈 상태, 오류, 권한 거부, 재연결 패턴
- 화상 세션과 대기방의 다크/미디어 중심 테마
- 채팅, 알림, 표·필터 등 고밀도 UI
- 관리자 화면과 데이터 시각화

따라서 `docs/design-system/`의 시스템을 그대로 복사하지 않고, **브랜드 기반층 + 제품 상태층 + 화면 패턴층**으로
확장해 `/frontend`의 단일 디자인 시스템으로 만든다.

## 3. 개편 목표와 비목표

### 3.1 목표

1. 첫 진입 5초 안에 Tika의 다정하고 시네마틱한 브랜드 인상을 전달한다.
2. 가입 → 온보딩 → 매칭 → 대기방 → 세션 → 평가 → 리포트 핵심 여정을 하나의 시각 언어로 연결한다.
3. 기능 목록을 나열하는 화면을 사용자의 다음 행동이 분명한 장면 중심 화면으로 바꾼다.
4. 공통 상태와 상호작용을 디자인 시스템 컴포넌트로 통일한다.
5. 모바일 320px부터 데스크톱 1440px까지 정보 위계와 주요 행동을 유지한다.
6. 영상이나 이미지가 로드되지 않아도 메시지와 기능이 온전히 동작하게 한다.

### 3.2 비목표

- API 계약, 인증 정책, 매칭 규칙, 세션 로직을 디자인 작업 중 임의 변경하지 않는다.
- Mobbin/Fixa의 로고, 카피, 이미지, UI를 그대로 복제하지 않는다. 구조와 리듬만 참고한다.
- 모든 화면을 랜딩 페이지처럼 만들지 않는다. 시네마틱 표현은 진입·전환·결과 화면에 집중한다.
- 출시 제외가 확정된 기능을 핵심 여정보다 먼저 고도화하지 않는다.
- 의미 없는 장식 애니메이션이나 모바일 패럴랙스를 추가하지 않는다.

## 4. 목표 경험 원칙

### 4.1 Human first

기능이나 점수보다 사람의 표정, 대화 장면, 관계의 변화를 먼저 보여준다. 분석 결과는 사용자를 심사하는
언어가 아니라 다음 대화를 돕는 근거로 표현한다.

### 4.2 One scene, one sentence, one action

한 화면 또는 한 주요 섹션에는 핵심 메시지 하나와 Primary CTA 하나만 둔다. 보조 행동은 텍스트 링크,
Secondary 버튼 또는 오버플로 메뉴로 낮춘다.

### 4.3 Calm over clutter

동일한 흰 카드의 반복을 줄이고 여백, 타이포그래피, 얕은 경계, 의미가 있는 면 색으로 영역을 구분한다.
사용자가 긴장하는 가입·매칭·세션 화면일수록 선택지를 줄이고 설명을 짧게 한다.

### 4.4 Editorial, not corporate

진입과 결과 화면은 대시보드보다 이야기의 흐름을 우선한다. 큰 사진 한 장, 짧은 문장, 숫자와 해석의
대비를 활용한다. 관리 화면처럼 밀도가 필요한 곳은 브랜드 색을 절제하고 기능성을 우선한다.

### 4.5 Accessible by default

텍스트 대비, 키보드 탐색, 44×44px 터치 타깃, reduced-motion, 미디어 폴백을 기본 계약으로 둔다.
색만으로 상태를 알리지 않고 아이콘과 라벨을 함께 제공한다.

## 5. 디자인 시스템 통합안

### 5.1 계층

```text
Primitive
  Klarna Pink / White / Chocolate / Ink / Leaf / Sun / Danger
        ↓
Semantic
  surface / text / border / action / status / focus / overlay
        ↓
Component
  Button / Field / Card / Nav / Modal / Media / Feedback / Session
        ↓
Pattern
  Auth / Onboarding / Matching / Waiting / Live Session / Report / Admin
```

### 5.2 색 역할

| 역할 | 기준 | 사용 원칙 |
|---|---|---|
| Page | White `#FFFFFF` | 일반 화면과 카드의 기본 배경 |
| Surface accent | Pale Pink `#FFF0F4` | 구분 면, 입력 보조 면, 상태 배경 |
| Primary text | Ink `#17120F` | 본문과 선명한 라벨 |
| Dark surface | Chocolate `#2F1D17` | 영상 스크림, 몰입 섹션, 다크 테마 |
| Brand / Action | Klarna Pink `#FFB3C7` | CTA, 선택 상태, 핵심 강조. Ink 라벨 사용 |
| Secondary | Warm Gray `#5D5659` | 설명, 캡션, 보조 아이콘 |
| Positive | Leaf 계열 | 성공, 연결됨, 강점 |
| Highlight | Sun `#F0C96B` | 포커스, 성장 포인트, 제한적 강조 |
| Brand text / Link | Chocolate `#5A382C` | 로고 텍스트, 링크, 섹션 라벨 |
| Affection | Deep Pink `#B8436D` | 하트와 감정 상태에 한정 |
| Danger | 별도 AA 충족 red ramp | 신고, 탈퇴, 세션 종료 전용 |
| Info | Pale Pink + Ink | 안내와 진행 상태. 액션과 혼동 금지 |

핑크는 CTA·선택·섹션 강조에 집중하고 콘텐츠 카드와 입력 면은 흰색으로 유지한다. 성공과 위험은 같은 브랜드색으로
억지 통합하지 않고, 의미와 접근성을 우선해 제품 상태 램프를 추가한다.

### 5.3 타이포그래피

- 기본 UI: Pretendard Variable 우선, SUIT/Noto Sans KR 폴백
- 감성 영문 강조: Cormorant Garamond Italic, 한 문장 중 1~3단어만 사용
- Display 48~72, H1 40~56, H2 32~40, H3 24~28, Body 16, Label 13을 반응형으로 적용
- 한국어 제목은 굵기와 자간으로 강조하고 무리한 영문 치환을 하지 않는다.
- 숫자 변화가 잦은 타이머·점수·통계에는 tabular-nums를 적용한다.

### 5.4 레이아웃과 반응형

- 기준 폭: 320, 390, 720, 840, 1280, 1440px
- 콘텐츠 최대 폭: 1280px, 긴 본문 최대 폭: 720px
- 좌우 여백: 모바일 20px, 태블릿 32px, 데스크톱 48~64px
- 그리드: 모바일 4열, 태블릿 8열, 데스크톱 12열
- `100vh` 대신 `100svh`와 safe-area inset을 사용한다.
- 주요 미디어 비율은 16:10, 16:9, 4:5, 1:1 중에서만 선택한다.

### 5.5 테마 정책

- 일반 제품 화면: White + Klarna Pink 기반 라이트 테마를 기본으로 한다.
- 세션, 대기방, 카메라 촬영: 미디어 가독성을 위한 Chocolate 기반 몰입 테마를 사용한다.
- OS 전역 다크모드는 1차 개편 범위에서 제외하는 안을 권장한다. 전역 다크까지 포함하면 모든 에셋과
  상태 조합의 QA 범위가 두 배가 되므로 별도 결정이 필요하다.

### 5.6 컴포넌트 전략

기존 React 래퍼의 동작·접근성 계약은 유지하고 외형과 API를 단계적으로 정리한다.

- 기본 카드는 반투명 White surface, 24px backdrop blur, 밝은 안쪽 하이라이트와 낮은 핑크 틴트 그림자를 사용한다.
- 글래스 뒤에는 Pale Pink 조명 레이어를 두되, 입력 필드와 Primary CTA는 불투명도를 높여 읽기와 조작성을 유지한다.
- 다크 미디어 화면의 글래스는 동일한 구조를 사용하되 어두운 반투명 surface로 전환한다.

유지 후 재스킨:

- Button, IconButton, Field, Select, Switch, Segmented, Modal, AlertDialog
- Card, Badge, Chip, Avatar, ListRow, EmptyState, Skeleton, Spinner, Progress, Steps
- Rating, ScoreRing, Callout, ConsentRow

신규 또는 구조 개편:

- `CapsuleNav`, `MobileNavSheet`, `CinematicHero`, `HeroHeadline`, `FloatingCTA`
- `EditorialMedia`, `StorySection`, `MetricStory`, `QuoteBlock`
- `PageHeader`, `FormShell`, `StatusPanel`, `MediaFallback`
- `SessionChrome`, `ConnectionBanner`, `CoachOverlay`, `ChatComposer`

마이그레이션 중에는 기존 `--bt-*` 토큰을 새 semantic 토큰의 호환 alias로 연결한다. 화면 전환이 끝난 뒤
레거시 prefix와 사용되지 않는 CSS를 제거한다. 한 번에 1,000여 개 참조를 치환하지 않는다.

## 6. 전역 정보 구조와 내비게이션

### 6.1 데스크톱

- 상단 중앙의 캡슐 내비게이션을 제품 셸에 맞게 확장한다.
- 좌측 로고, 중앙 핵심 메뉴, 우측 알림/프로필의 3영역으로 구성한다.
- 스크롤 전에는 미디어 위 inverse, 스크롤 후에는 Paper 표면으로 전환할 수 있다.
- 메뉴는 실제 출시 범위만 노출한다. 준비 중 기능을 동일 위계의 탭으로 두지 않는다.

### 6.2 모바일

- 핵심 탭이 4개 이하라면 하단 내비게이션을 유지한다.
- 5개 이상일 때는 `마이`를 프로필 진입점과 통합하거나 전체 메뉴 시트로 이동한다.
- 히어로가 있는 화면에서는 로고 + 메뉴 버튼만 남기고 전체 메뉴는 full-screen sheet로 연다.
- 고정 UI는 safe-area를 포함하고 콘텐츠/CTA를 가리지 않아야 한다.

### 6.3 몰입 화면

대기방, 세션, 촬영, 챗봇 대화는 일반 AppShell 밖에 둔다. 뒤로가기, 종료, 연결 상태처럼 현재 과업에
필수적인 컨트롤만 남기고 전역 메뉴는 숨긴다.

### 7.1 브랜드 진입과 인증

- Splash는 로고 애니메이션 자체보다 로그인 상태 판정 중이라는 사실과 정적 폴백을 우선한다.
- Login은 데스크톱에서 미디어와 폼의 7:5 분할, 모바일에서 4:5 히어로 위 폼 시트 구조를 권장한다.
- 소셜 로그인 로고는 각 브랜드 원색을 허용하는 예외로 명시한다.
- 오류는 필드 바로 아래에서 설명하고 입력값을 지우지 않는다.

### 7.2 온보딩

- 모든 단계에 현재 위치, 남은 단계, 저장/재개 가능 여부를 보여준다.
- 한 화면의 질문 수와 선택 수를 줄이고 다음 CTA는 선택 완료 후 명확히 활성화한다.
- 얼굴 촬영은 권한 요청 전 이유를 설명하고, 거부/기기 없음/분석 실패/재촬영 상태를 각각 설계한다.
- 동의 화면은 필수와 선택을 시각적으로 구분하되 선택 동의를 불리하게 보이게 하지 않는다.

### 7.3 홈

현재의 균등한 대시보드 카드 4개보다 다음 순서로 재편한다.

1. 사용자 인사와 오늘의 한 문장
2. 예정된 세션 또는 새 매칭이라는 단일 Primary 행동
3. 최근 대화에서 발견한 한 가지 성장 포인트
4. 최근 리포트/연습 기록

예정 세션이 없을 때 가짜 통계나 빈 카드로 공간을 채우지 않는다. 실제로 가능한 다음 행동을 큰 장면으로
보여준다. 시네마틱 비주얼은 배경 전체가 아니라 핵심 행동 영역에 제한적으로 사용할 수 있다.

### 7.4 매칭

- 트랙 선택은 기능 비교표보다 “누구와, 어떤 방식으로 연습하는가”를 장면 카드로 표현한다.
- 대기 화면은 예상 시간, 취소, 백그라운드 알림 여부를 명확히 제공한다.
- 매칭 카드에는 공개가 허용된 정보만 노출하고 수락/거절의 결과를 사전에 설명한다.
- 시간 만료, 상대 취소, 중복 요청, 네트워크 재시도 상태를 `StatusPanel`로 통일한다.

### 7.5 대기방과 실시간 세션

- 영상이 주인공이며 도구막대는 화면 가장자리의 반투명 Ink 캡슐로 둔다.
- 마이크/카메라 꺼짐은 중립, 통화 종료만 danger를 사용한다.
- 연결 중, 연결됨, 불안정, 재연결, 종료 상태를 텍스트+아이콘으로 제공한다.
- 코칭은 한 번에 하나만, 상대 얼굴과 주요 컨트롤을 가리지 않는 작은 오버레이로 표시한다.
- reduced-motion에서는 코칭과 컨트롤의 이동을 즉시 전환으로 대체한다.

### 7.6 평가, 피드백, 리포트

- 평가는 한 질문씩 진행하고 현재 진행률과 익명/공개 범위를 먼저 설명한다.
- 피드백은 점수 순위가 아니라 `관찰 → 의미 → 다음에 해볼 행동` 순서로 쓴다.
- 리포트 첫 화면에는 핵심 해석 하나와 다음 연습 CTA 하나만 둔다.
- 차트는 보조 근거이며 색 외에 라벨, 수치, 패턴으로도 구분한다.
- 데이터 없음, 생성 중, 생성 실패 상태에서 가짜 점수를 보여주지 않는다.

### 7.7 계정과 설정

- MyPage는 프로필 요약, 개인정보, 동의, 계정 보안의 4영역으로 정리한다.
- 수정 화면은 공통 `FormShell`을 사용하고 저장 중 이탈 방지와 서버 오류 복구를 제공한다.
- 회원 탈퇴, 차단 해제 등 위험 행동은 일반 설정과 시각적으로 분리하고 확인 다이얼로그를 거친다.

### 7.8 챗봇

- 대화 영역을 우선하고 설정/리포트는 별도 장면으로 분리한다.
- 사용자와 AI 말풍선은 색뿐 아니라 정렬, 라벨, 아바타로 구분한다.
- 입력 중, 응답 생성 중, 재시도, 중단, 세션 만료 상태를 공통화한다.
- AI 추정과 조언에는 단정하지 않는 문장 규칙과 참고용 표시를 유지한다.

### 7.9 관리자

관리자는 Paper/Ink 기반의 고밀도 UI를 쓰되, 시네마틱 미디어와 큰 감성 카피는 적용하지 않는다.
필터, 표, 페이지네이션, 일괄 작업, 위험 작업 확인이 먼저다. 현재 출시 보류 제안이 있으므로 P0 화면 완료 후
별도 스프린트로 다룬다.

## 8. 공통 상태 명세

모든 데이터 화면은 다음 상태를 디자인하고 구현해야 한다.

| 상태 | 최소 표현 |
|---|---|
| Initial | 제목과 페이지 골격은 즉시 표시 |
| Loading | 레이아웃을 보존하는 Skeleton, 중복 제출 방지 |
| Empty | 비어 있는 이유 + 가능한 다음 행동 |
| Error | 사용자 언어의 원인 + 재시도/대체 경로 |
| Offline | 연결 끊김 표시 + 재연결 상태 |
| Partial | 일부 데이터 누락을 숨기지 않고 가능한 내용은 유지 |
| Permission denied | 권한이 필요한 이유 + 설정 이동/대체 행동 |
| Success | 완료 결과 + 다음 화면 또는 되돌리기 가능 여부 |

## 9. 콘텐츠와 에셋 원칙

- 헤드라인은 기능명이 아니라 사용자가 느끼게 될 변화를 쓴다.
- 설명은 1~2문장, CTA는 동사로 시작한다.
- 의미 없는 “특별한”, “감성적인” 대신 실제 장면과 행동을 쓴다.
- Mobbin 스크랩(`Fixa _ Mobbin.html`)과 캡처 이미지는 **저장소에 두지 않는다** — 제3자 사이트 원본이라 참고 전용이며 배포 에셋으로도 쓰지 않는다.
- 현재 `hero-couple.webp`는 우선 poster 후보로 사용하되 피사체가 작아 모바일용 별도 크롭/소스가 필요하다.
- 메인 홈은 `public/main_hero_video.mp4`를 사용한다. 4:3 원본을 데스크톱 16:10으로 쓰면
  상하가 잘리고, 모바일 4:5로 쓰면 좌우 크롭이 커지므로 breakpoint별 `object-position`과 안전영역을
  와이어프레임에서 검증한다.
- 현재 720×540 영상은 대형 데스크톱에서 업스케일 흔적이 보일 수 있다. 가능하면 같은 편집본을
  1920×1080 이상으로 재출력하고 모바일 4:5 또는 9:16 버전을 별도로 준비한다.
- 이미지 경로는 컴포넌트에 하드코딩하지 않고 콘텐츠 데이터로 주입한다.
- 첫 화면 poster만 eager/high priority, 나머지는 lazy load한다.
- 영상은 MP4/WebM 이중 소스와 poster 폴백을 제공하고 파일당 4MB 이하를 목표로 한다.

## 11. QA와 완료 기준

### 기능

- 기존 라우트, API 호출, 권한 가드, 세션 이벤트 동작을 유지한다.
- 가입 → 리포트 핵심 여정을 중단 없이 완료할 수 있다.
- Loading/Empty/Error/Offline 상태에서 막다른 화면이 없다.

### 시각

- 320, 390, 720, 840, 1280, 1440px에서 텍스트 충돌과 가로 스크롤이 없다.
- 한 화면에 Primary CTA가 하나다.
- 이미지/영상 비율이 고정돼 CLS가 발생하지 않는다.
- 직접 입력한 색은 서드파티 로고 등 승인된 예외만 남는다.
- 레거시 BloomTalk/티키타카 표기가 최종 브랜드 정책에 맞게 정리된다.

### 접근성

- 일반 텍스트 4.5:1, 큰 텍스트와 비텍스트 UI 3:1 이상 대비를 확보한다.
- 모든 주요 기능을 키보드만으로 사용할 수 있다.
- 포커스 링이 배경과 구분되고 모달/시트의 포커스가 올바르게 관리된다.
- 터치 타깃은 최소 44×44px다.
- reduced-motion에서 영상 자동 재생과 큰 이동 모션이 정지 또는 즉시 전환된다.
- 스크린 리더에서 상태 변경과 폼 오류가 안내된다.

### 성능

- 첫 화면 콘텐츠는 영상 로딩과 무관하게 즉시 표시한다.
- hero poster를 제외한 이미지와 영상은 지연 로드한다.
- 모바일에서 장식 미디어가 핵심 상호작용을 지연시키지 않는다.
- 제작 빌드와 lint가 통과하고 주요 콘솔 오류가 없다.

## 14. 권장 착수 순서

결정 대기 중에도 안전하게 시작할 수 있는 순서는 다음과 같다.

1. 현재 화면/상태 스크린샷 수집과 회귀 체크리스트 작성
2. Tika 색·타입·간격 토큰과 제품 상태 토큰 초안 작성
3. Button, Field, Card, Modal, StatusPanel을 Gallery에서 검증
4. AppShell과 Login을 첫 파일럿 화면으로 개편
5. 파일럿 리뷰 후 온보딩과 핵심 여정으로 확장

Login은 브랜드 표현을, AppShell은 제품 내비게이션을, Gallery는 공통 컴포넌트를 동시에 검증할 수 있어
초기 방향을 가장 빠르게 확인할 수 있는 조합이다.
